# Regime C: the borrow composition, and a build-check correction

[FACT] `const_write_proj_local_simulation` (const_write.lean, commit
036c9ad) closes regime C's core: `loc.field := v` at a nonzero offset
over a bound root local. The shape that makes it interesting is the
ASYMMETRY — the source performs exactly ONE permission event (a write
through the root's tag), while the target performs THREE (`Borrow(Mut)`,
`CStore` through the fresh tag, `Die`). BRIDGE 1
(`sb_ref_use_die_cancels`, closed 2026-08-15) says those three have the
net stack effect of the one, up to the tag counter; this proof is the
first consumer of that keystone, and it is the piece every remaining
non-local regime needs.

[FACT] Three pieces had to be built to make BRIDGE 1 usable, all of
which generalize:
- `sb_ref_Mut_ok_of_sb_write`: the internal borrow has NO source
  counterpart, so its success cannot be transported — it is derived from
  the *target* write's success (per cell, a `Mut` retag IS that write
  followed by a `pushCell` that cannot fail). This is the general answer
  to "how does a compiler-internal event get its success obligation?".
- `isProtectedIn_NextTag_false` / `NextTag_ne_wildcard`: BRIDGE 1's two
  side conditions (the fresh tag is neither protected nor the wildcard),
  DERIVED rather than assumed. The argument is pleasing: protector
  frames on the target are ρt images of source frames, and
  `TagRenameBound` puts every image strictly below the counter, so the
  counter itself cannot appear in a frame. No new invariant needed.
- `PermSim.congr_target`: `PermSim` depends only on the three lists and
  a counter inequality, so BRIDGE 1's equations move the relation from
  the "bare parent write" state to the actual post-`Die` state.

[FACT] ρt does NOT grow in regime C, unlike the ref leaf. The internal
fresh tag is never entered into the rename map — which is precisely why
compiler temp borrows stay invisible to the invariant, and why this
regime needed no rename-extension bookkeeping at all.

[FACT] `LocalBindingSim` gained a block-domain conjunct (`∀ k <
blockSize τ, ρa (binding.addr + k) ∈ dom`). A projected write targets
`binding.addr + offset`, so BRIDGE 2's `h_dom` obligation cannot be met
from the base address alone. It mirrors `MemValSim`'s existing
referent-range conjunct and costs nothing in the closed regimes.

[EMP] (Lean 4.28, verified against 036c9ad) **`lake build` does not
build the proof libraries.** Only `Core` (`obseq`/`obseq2`/`interp`) is
a `@[default_target]`; the proof libs are `Obseq2Proof`/`Obseq3Proof`
and must be named explicitly. Symptom that exposed it: edits to
`common.lean` appeared to have no downstream effect — deleting
`common.olean` and running `lake build` did not even recreate it. Any
"build green" claim from plain `lake build` says nothing about the
proofs. notes/CLAUDE.md corrected accordingly.

[EMP] More Lean 4.28 potholes, all cheap once recognized:
- `set x := e with h` is Mathlib-only; this project has no Mathlib, so
  it fails with a bare "unknown tactic" that then CASCADES into
  top-level parse errors far below ("unexpected identifier; expected
  'binder_predicate'…"). When such a parse error appears, look upward
  for an unknown tactic before touching the reported line.
- The metavariable-leak pattern from the ref leaf recurred: three
  `omega` failures whose printed counterexample atoms did not include
  the goal's own variables, all of which vanished once genuine errors
  elsewhere in the block were fixed.
- `refine ⟨_, n, ?_, ?_⟩` where the underscore is the final machine
  state cannot be solved from a later `rw`-then-`exact`; write the state
  explicitly (record update of a record update is defeq to the step
  lemma's output, so `exact` still closes it).
